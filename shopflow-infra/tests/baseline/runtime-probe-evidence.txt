RUNTIME PROBE EVIDENCE - database provisioning, seed reset, provider contract
================================================================================

Owner: shopflow-infra. Captured 2026-09-17 (Docker 28.2.2, Compose v2.37.1, Node v24.14.0,

WHY THIS FILE EXISTS
--------------------
Acceptance criteria 2, 3, 6 and 7 are end-to-end criteria for the nine-service stack, and the
stack as a whole cannot run in this workspace yet because four of the six composed repositories
are missing (see README.md "Status of this delivery" and guard G6). However, three of the nine
services - `orders-db`, `inventory-db`, `notifications-db` - and the unchanged provider emulator
have NO dependency on those repositories. They were therefore started and probed directly, so the
database provisioning, the deterministic seed, the reset semantics and the provider contract are
verified with real Docker containers instead of being asserted.

METHOD
------
The probe ran from `C:\Users\SEBRH\lindesk-db-probe`, a byte-identical copy of the delivered
`docker-compose.yml`, `postgres/*-init.sql` and `notification-emulator/`. The copy was necessary
because of an environment-level defect of Docker Desktop for Windows, reproduced independently of
this repository:

  * a minimal, unrelated compose project (three lines of YAML, `select 1;` as the init script)
    with the SAME bind mount into `/docker-entrypoint-initdb.d` FAILS with
    `ls: /docker-entrypoint-initdb.d/...: I/O error` when its directory is at a long path
    (reproduced at this workspace path and at a synthetic ~130-character path), and
  * the SAME minimal project SUCCEEDS at a short path (`C:\Users\SEBRH\...` or `%TEMP%`).

  In other words: for paths of this length, Docker Desktop serves bind-mounted files to a non-root
  container user with EIO. The postgres 17 entrypoint then fails its own guard
  (`ls /docker-entrypoint-initdb.d/ > /dev/null`, which runs as the `postgres` user) and exits 1.
  The delivered compose file is not involved: the identical file bytes, the identical target path
  and the identical compose structure all succeed at a short path, and the same failure occurs with
  a three-line unrelated compose file at this path length.

  Consequence: `docker compose up --build -d` from this workspace directory cannot start ANY
  database container (all three exit 1) regardless of how the compose file is written. Running the
  same compose file from a short path works. This affects the evaluation workspace path only, not
  the deliverable.

WHAT IS PROVEN HERE
-------------------
1. All three database services reach `healthy` with their own image, credentials, volume and init
   script (`docker compose ps --format json` -> `"Health":"healthy"`, `ExitCode: 0`).
2. No database service publishes a host port: `Publishers[].PublishedPort = 0` for every database
   service, `docker compose port <db> 5432` -> not published, and `PORTS` shows only `5432/tcp`.
3. Each database contains exactly its owner's schema and nothing else:
     orders-db        -> orders, order_operations, notification_outbox   (owner: orders)
     inventory-db     -> products, stock_decrements                      (owner: inventory)
     notifications-db -> notifications, notification_attempts            (owner: notifications)
   No database contains another service's table, so the shared schema of `postgres/init.sql` has no
   successor: ownership is enforced at the data level, not only in the compose topology.
4. The deterministic seed is applied from `postgres/inventory-init.sql` unchanged:
     product-a | SKU-A | Product A | 1200 | stock 10
     product-b | SKU-B | Product B | 2500 | stock 5
   and the orders and notifications tables start empty (0 rows).
5. Reset semantics: after mutating the data (stock 10 -> 3, one order row, one notification row),
   `docker compose down -v` followed by `docker compose up -d` restores exactly the seed
   (`product-a=10`, `product-b=5`, orders 0, notifications 0) with all three services healthy again.
6. The unchanged provider emulator builds, passes its healthcheck and speaks its contract on host
   port 4010 (published, as specified):
     GET  /health                          -> 200 {"ok":true}
     POST /notifications (valid)           -> 201 {"id":"notification-0001","type":"ORDER_CONFIRMATION",
                                                  "orderId":"...","customerEmail":"buyer@example.com"}
     POST /notifications (wrong type)      -> 400 {"error":"Invalid notification"}
     POST /notifications (no orderId)      -> 400 {"error":"Invalid notification"}
     GET  /notifications                   -> 200 [ the stored record, in arrival order ]
   The record echoes exactly the three legacy fields and the id is sequential (`notification-0001`),
   matching the unchanged provider contract.

WHAT IS NOT PROVEN HERE
-----------------------
The application services (`web`, `gateway`, `orders`, `inventory`, `notifications`) were not started:
their build contexts (`../shopflow-web`, `../shopflow-orders`, `../shopflow-inventory`,
`../shopflow-notifications`) do not exist in this workspace, which is the blocker recorded in
tests/baseline/README.md. Therefore P1-P10 and criteria 2, 3 (application half), 7 and 8 remain
unverified, and no HTTP behaviour of the public API on port 3001 is claimed.

------------------------------------------------------------------------------------
  docker compose up -d orders-db inventory-db notifications-db

  docker compose exec -T notifications-db psql -U notifications -d notifications -c "\dt"
  docker compose exec -T notifications-db psql -U notifications -d notifications -tAc "select (select count(*) from notifications),(select count(*) from notification_attempts)"
  # reset semantics
  docker compose exec -T inventory-db     psql -U inventory     -d inventory     -c "update products set stock = 3 where id = 'product-a'"
  docker compose exec -T orders-db        psql -U orders        -d orders        -c "insert into orders (...) values (...)"
  docker compose exec -T notifications-db psql -U notifications -d notifications -c "insert into notifications (...) values (...)"
  docker compose down -v
  docker compose up -d orders-db inventory-db notifications-db
  # provider contract (host port 4010)
  docker compose up -d --build notification-emulator
  curl -s -i http://localhost:4010/health
  curl -s -i -X POST http://localhost:4010/notifications -H "content-type: application/json" \

ADDENDUM - provider stop/start semantics, and the P6 defect it exposed  
================================================================================  
  
Command: docker compose up -d notification-emulator; POST one confirmation;  
docker compose stop notification-emulator; docker compose start notification-emulator  
  
Findings: stop leaves the service unreachable - curl reports HTTP code 000 - and start brings it  
back healthy. The emulator stores its records in the provider process memory, so the restart returns  
an EMPTY inspection list: the record posted before the stop is gone after the start.  
This is consistent with the provider contract - the provider owns no durable state and must not be  
given any - but it invalidated the first P6 implementation, which counted records against a  
pre-outage baseline and would therefore have failed on a correctly working stack. P6 now accepts  
both outcomes for the provider list - reset or preserved - and keys its assertions on the order id.

ADDENDUM - database restart invariant: an initialised database is not re-seeded  
================================================================================  
  
Command: docker compose up -d orders-db inventory-db notifications-db; mutate stock 10 to 3 and insert  
one order row; docker compose stop inventory-db orders-db; docker compose start inventory-db orders-db.  
  
Result: after the restart the database still reports product-a=3, product-b=5 and 1 order row and  
all three services are healthy again. The init scripts run only when a volume is created, so a  
restart never re-seeds and never wipes data - the invariant the recovery scenario P9 and the  
reset semantics of the README depend on.
