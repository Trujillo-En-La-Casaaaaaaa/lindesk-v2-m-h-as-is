GATEWAY PROBE EVIDENCE - the one implemented application service

WHY THIS FILE EXISTS
--------------------
`shopflow-gateway` is the only Wave 3 repository that is implemented in this workspace, so its image
- built from exactly the context the delivered `docker-compose.yml` names - can be run on its own.
This probe therefore verifies the parts of acceptance criterion 7 that do not need the orders and
inventory services: the gateway's liveness route, its route table (including the path rewrite), the
documented `503 UNAVAILABLE` failure envelope, the prohibited routes and the healthcheck command that
the compose file uses for all four Node services.

METHOD
------
The gateway was started OUTSIDE compose, on purpose: its `depends_on` edges (`orders`, `inventory`,
`condition: service_healthy`) cannot be satisfied while those repositories are missing, and compose
would refuse to start it. The probe is therefore an isolated service probe, not a composed-stack run:

  docker build -t gw-probe ../shopflow-gateway                    # the context the compose file uses
  docker run -d --name gw-probe -p 3001:3001 \
      -e PORT=3001 -e ORDERS_URL=http://orders:3002 \
      -e INVENTORY_URL=http://inventory:3003 -e UPSTREAM_TIMEOUT_MS=5000 gw-probe

The two upstream URLs are the delivered compose values; outside the compose network those hostnames do
not resolve, which is exactly the transport-failure path the public contract documents as the new
`503` failure mode.

WHAT IS PROVEN HERE
-------------------
1. The gateway image builds from the build context the delivered compose file declares, publishes
   `0.0.0.0:3001->3001/tcp` and reports `(healthy)`.
2. `GET /health` -> `200 {"ok":true}` with a generated `x-correlation-id`, while both upstreams are
   unreachable: liveness does not depend on the upstreams, as the frozen public contract requires.
3. Every proxied public route answers the documented `503` envelope
   `{"error":"Upstream service unavailable","code":"UNAVAILABLE"}` when its owning service cannot be
   reached: `GET /products`, `POST /orders`, `GET /orders/:id` and `POST /admin/orders/:id/ship`
   (the last one proving the documented `/admin/orders/:id/ship` -> `/orders/:id/ship` route mapping
   exists and is proxied rather than answered locally).
4. The prohibited routes do not exist: `POST /orders/:id/cancel` -> `404 {"error":"Not found","code":"NOT_FOUND"}`
   and `DELETE /orders/:id` -> `404`, as does any unknown path. The gateway answers these itself; no
   new public capability is reachable.
5. `cors()` is enabled (`Access-Control-Allow-Origin: *` on every response), as before the migration.
6. The exact healthcheck command the compose file uses for `gateway`, `orders`, `inventory` and
   `notifications`
   (`node -e "fetch('http://localhost:3001/health').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"`)
   returns exit code 0 inside the container, so that healthcheck form is proven to work on
   `node:22-alpine`.

WHAT IS NOT PROVEN HERE
-----------------------
No success path is claimed: with the orders and inventory services missing, `GET /products`,
`POST /orders`, `GET /orders/:id` and ship cannot reach a 200/201/404/409 domain response, and the
`web` service cannot be built at all. Criterion 7's domain responses, the whole of P1-P10 and criteria
2, 3 (application half), 4, 8 therefore remain unverified; the gateway's own liveness, failure and
prohibition behaviour is what this probe covers.
